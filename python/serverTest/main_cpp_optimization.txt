main.cpp optimization opportunities
===================================

Priority 1: low-risk, high-impact changes
-----------------------------------------

1. Enable OpenMP for the server target

The numerical helper loops use OpenMP pragmas, but the CMake server target is
currently compiled with only -O3 -DNDEBUG. Add find_package(OpenMP REQUIRED)
and link OpenMP::OpenMP_CXX to zeromq_cpp_server_ex.

Benchmark thread settings after enabling it because clusters already run in
parallel. Parallelizing both across clusters and within each cluster can
oversubscribe the machine.

2. Cache Jp^T Jp across trust-region retries

UpdateStepSizeAndSolve computes Jp^T Jp before the retry loop and then computes
it again inside every retry. Jp does not change during these retries. Keep the
original block-diagonal matrix and derive each retry's Ul from the cached
matrix.

Expected benefit: substantial when trust-region steps are rejected.

3. Cache retry-invariant Schur quantities

SolveByGDNesterov currently recomputes the following on every trust-region
retry:

  W = Jp^T Jl
  bp = Jp^T residual
  bl = Jl^T residual
  proximal products involving cameras and cameras_s

These quantities are constant during the retry loop. Compute them once before
while (true) and pass them into SolveByGDNesterov.

Priority 2: reduce allocations and repeated arithmetic
-------------------------------------------------------

4. Reuse Nesterov workspace vectors

The Nesterov iteration creates dynamic intermediate vectors for:

  W^T x
  V^-1 W^T x
  W V^-1 W^T x
  U^-1 W V^-1 W^T x

Preallocate these vectors once per solve and fill them with Eigen noalias()
assignments. Reuse buffers for g, yk, and y0 as well. This avoids repeated heap
allocations in a loop that can execute up to 100 times.

5. Avoid redundant proximal block products

Instead of computing S*c and S*c_s separately, compute S*(c-c_s) once. Cache
this value for the retry loop.

The end penalty can also be evaluated as:

  P(c + delta) = P(c)
                 + 2 * delta^T * S * (c-c_s)
                 + delta^T * S * delta

This can reduce two block products per retry to one. Change blockMult to write
into a reusable output vector rather than allocating and returning a new one.

Implementation status (2026-07-24)
----------------------------------

Items 2-5 are implemented cumulatively in main.cpp:

  - Jp^T Jp is cached across trust-region retries.
  - W, Jp^T residual, Jl^T residual, and the proximal gradient are cached.
  - Nesterov Schur-product and iteration vectors are reused.
  - S*(c-c_s), the starting penalty, and a reusable S*delta buffer replace
    redundant proximal block products.

The server builds successfully. Thirty-iteration checks preserve the stored
rounded trajectories for problems 52 and 744. Problem 52 single-run timings
varied by about 2.3 percent across near-identical builds, so performance should
be judged from the complete 30-part benchmark rather than individual short
runs. Results are stored under the "# optimized 2-5" section.

6. Make the stopping test cheaper

The CPU stopping test computes xk.norm() and g.norm() every iteration. Compare
squared norms instead to avoid square roots:

  (i+1)^2 * ||g||^2 < (eps * Lip)^2 * ||xk||^2

The reductions remain, but this removes two square roots. Unlike on GPU,
checking only every k iterations is less important because no device-host
synchronization is involved.

Implemented 2026-07-24: the stopping helper now compares xk.squaredNorm() and
g.squaredNorm() using the algebraically equivalent squared inequality.

Priority 3: thread and data-management cleanup
----------------------------------------------

7. Fix the Eigen thread-count edge case

threads_per_cluster is clamped to at least one for Ceres, but
Eigen::setNbThreads receives the unclamped integer division. If numClusters is
greater than 31, Eigen receives zero and may restore its default thread count.
Pass threads_per_cluster to both Eigen and Ceres.

Fixed 2026-07-24: Eigen and Ceres now both receive the clamped
threads_per_cluster value.

8. Cache sparse Jacobian structure

GetJacobianAndResidual reconstructs the Jp and Jl sparse structures on every
update even though observation-to-camera and observation-to-landmark mappings
are fixed after ResetProgram. Cache the compressed row/column structure and
only overwrite numerical values.

9. Reduce request and thread overhead

Use const references for protobuf submessages where their lifetime permits it,
for example request_p.program(), to avoid copying large messages.

Detached OS threads are also created for every request. A fixed worker pool
would reduce thread creation overhead and make concurrency limits explicit.
This is probably secondary to the numerical work for large problems.

Priority 4: larger algorithm-preserving representation change
--------------------------------------------------------------

10. Accumulate block Hessians directly

Jp^T Jp and Jl^T Jl are block diagonal because each observation depends on one
camera and one landmark. Generic Eigen sparse multiplication performs symbolic
processing and allocations that are unnecessary for this structure.

Accumulate 9x9 camera blocks and 3x3 landmark blocks directly from Jacobian
rows. This likely has the largest long-term CPU potential, but it is a larger
change and requires numerical equivalence tests.

Build-level options
-------------------

The build already uses -O3. For a server deployed on fixed hardware, benchmark
-march=native and link-time optimization. These are expected to provide modest
wins compared with removing repeated sparse products and allocations.

Recommended implementation order
--------------------------------

1. Enable OpenMP and fix the Eigen thread count.
2. Cache Jp^T Jp and retry-invariant Schur quantities.
3. Reuse Nesterov buffers and remove redundant proximal products.
4. Profile the updated code.
5. Implement direct block-Hessian accumulation only if profiling still shows
   sparse Hessian construction as a major cost.

Validation
----------

For each optimization, compare:

  - total and solver-only runtime,
  - final cost, bestCost30, and bestCost60,
  - trust-region rejection count,
  - average Nesterov iterations,
  - numerical agreement of accepted delta_p and delta_l steps.

OpenMP and thread-count changes should be benchmarked at representative cluster
counts to detect oversubscription.

Second performance review (2026-07-24)
======================================

Item 10 result
--------------

Direct accumulation of the 9x9 camera and 3x3 landmark Hessian blocks was
implemented and reproduced the established problem 52 and problem 744
trajectories. The partial full-suite benchmark showed no meaningful runtime
change, so the experiment was stopped.

This implementation optimized only Jp^T Jp and Jl^T Jl. It still constructed
sparse Jp and Jl, used Ceres to evaluate the full Jacobian, and separately
formed W, bp, and bl. Optimizing these two products alone is too narrow. Do not
invest further in the standalone BlockDiagonalJtJ approach unless profiling
shows that it becomes significant after larger changes.

11. Reduce weighted autodiff from 105 variables to 12
------------------------------------------------------

Status: implemented and retained.

SnavelyReprojectionErrorWeighted was declared with parameter block
dimensions:

  9 + 3 + 9 + 3 + 81 = 105

Only the camera and landmark blocks, with 12 values in total, are variables.
cameraWeight, pointWeight, and cameraTransform are registered as constant
parameter blocks.

Store pointers to the weight and transform arrays in each residual functor and
expose only camera and landmark to AutoDiffCostFunction:

  AutoDiffCostFunction<..., 2, 9, 3>

The referenced arrays remain at stable addresses after ResetProgram;
preconditioning updates overwrite their values in place. This should reduce
the Jet dimension and arithmetic performed during every Jacobian evaluation.

Focused 30-iteration checks reproduced the established trajectories exactly:

  problem 52:  9.78 s, bestCost 485348, bestIt 29
  problem 744: 94.82 s, bestCost 3093408, bestIt 26

These were approximately twice as fast as the previous checks. A partial
full-suite run recorded 13 additional 90-iteration problems before it was
stopped intentionally because quality remained identical and the speedup was
already decisive. Keep this optimization.

12. Fuse CRS extraction and normal-equation assembly
-----------------------------------------------------

Status: implemented and retained.

The previous path performed the following separate operations:

  1. Ceres produces a CRS Jacobian.
  2. GetJacobianAndResidual reconstructs sparse Jp and Jl.
  3. Ul and Vl are formed from Jp and Jl.
  4. Eigen separately forms W, bp, and bl.
  5. Jp and Jl are retained for the predicted quadratic cost.

Consume each Ceres CRS row once and accumulate all retry-invariant quantities:

  U  = Jp^T Jp
  V  = Jl^T Jl
  W  = Jp^T Jl
  bp = Jp^T residual
  bl = Jl^T residual

The predicted quadratic cost can then be evaluated without Jp and Jl:

  ||r + Jp*dp + Jl*dl||^2
    = ||r||^2
      + 2*bp^T*dp + 2*bl^T*dl
      + dp^T*U*dp + 2*dp^T*W*dl + dl^T*V*dl

This removes sparse Jp/Jl construction and several downstream sparse products,
rather than optimizing only U and V as item 10 did.

The fused path now consumes each Ceres CRS row directly to build U, V, W, bp,
and bl. The trust-region predicted cost uses the equivalent normal-equation
quadratic, so Jp and Jl are no longer needed by the active local solve.

Focused 30-iteration checks reproduced the established trajectories exactly:

  problem 52:  9.58 s versus 9.78 s (2.1 percent faster)
  problem 744: 94.46 s versus 94.82 s (0.4 percent faster)

For problem 744, excluding partitioning, solve time improved from about 78.27 s
to 77.81 s (0.6 percent). The gain is modest but consistent, and the fused
representation is the required foundation for item 13's block-edge Schur
operator. Keep this optimization.

13. Use a block-edge Schur operator
-----------------------------------

Status: implemented and retained after expanded validation.

W has a natural 9x3 camera-landmark block structure. Store it as a list of
camera-landmark edges and implement blockwise products for:

  W^T*x
  V^-1*W^T*x
  W*V^-1*W^T*x
  U^-1*W*V^-1*W^T*x

These products execute in every Nesterov iteration, up to 100 times per solve.
A block-edge operator avoids repeated generic Eigen sparse traversal and fits
naturally with the fused assembly in item 12.

Three block-edge traversal variants were implemented and benchmarked. All
reproduced the stored problem 52 and problem 744 endpoints, but performance
depended strongly on the traversal and problem.

The best problem 52 run improved from 9.58 s with sparse W to 8.05 s, about
16 percent. On problem 744, however, fused sparse W took 94.46 s overall and
77.81 s excluding partitioning. The block-edge variants took:

  camera-row traversal: 100.13 s overall, 83.48 s solve-only
  scalar edge traversal: 98.49 s overall, 81.80 s solve-only
  fixed-size Eigen edge traversal: 99.45 s overall, 82.38 s solve-only

The initial two-problem result was not representative enough to reject the
optimization. Additional matching 90-iteration comparisons produced exact
bestCost30, bestCost60, final cost, and best iteration values:

  problem 394:  solve-only 42.26 s -> 36.26 s (14.2 percent faster)
  problem 1064: solve-only 44.01 s -> 36.22 s (17.7 percent faster)

Across problems 52, 394, 744, and 1064, the scalar edge traversal wins three
of four comparisons. Its geometric-mean speedup is 10.5 percent overall and
11.4 percent solve-only. Aggregate elapsed time improves 5.6 percent and
aggregate solve-only time improves 6.5 percent.

Retain the scalar edge traversal. Problem 744 remains an important exception:
it regresses 4.3 percent overall and 5.1 percent solve-only. A future layout
should target that case with contiguous structure-of-arrays storage or
landmark-oriented adjacency rather than the slower camera-row or fixed-size
Eigen traversals tested here.

14. Avoid unused residual output in GetCost
-------------------------------------------

GetCost currently allocates a std::vector<double> and asks Ceres to fill all
residual values, but only the scalar cost is read. Pass nullptr for residuals:

  problem.Evaluate(evalOptions, &cost, nullptr, nullptr, nullptr)

This is behavior-preserving and applies to every trust-region attempt,
including rejected attempts, as well as explicit cost requests. This is the
lowest-risk remaining runtime change.

15. Reuse Ceres evaluation workspaces
-------------------------------------

Status: implemented and retained after a fixed ten-problem benchmark.

Each Jacobian or cost call reconstructs EvaluateOptions, copies
function_residual_blocks, and creates new CRS and residual containers. Keep
per-program members for:

  - ceres::Problem::EvaluateOptions,
  - ceres::CRSMatrix,
  - residual storage,
  - Jacobian conversion and normal-equation buffers.

The normal-equation path now initializes EvaluateOptions once per program and
reuses the CRS matrix, residual vector, and dense camera/landmark block
buffers. Numeric buffers are cleared in place before each assembly. Relative
to the retained persistent-edge implementation, all ten problems reproduced
bestCost30, bestCost60, final cost, and best iteration exactly. Performance
improved by:

  geometric-mean overall:    2.58 percent
  aggregate overall:         2.15 percent
  geometric-mean solve-only: 2.75 percent
  aggregate solve-only:      2.54 percent

Keep this optimization.

16. Represent U, V, and their inverses as dense blocks
------------------------------------------------------

Status: tested and rejected.

U and V are always block diagonal, but SolveByGDNesterov copies them as sparse
matrices before replacing each block with its inverse. Store contiguous
std::vector<Eigen::Matrix<double, 9, 9>> and 3x3 equivalents instead.

Perform damping, inversion, and matvecs directly on these blocks. Benchmark
LDLT.solve(I) against the current general matrix inverse for speed and numerical
agreement.

The dense-block experiment produced mixed timing with no reliable
geometric-mean improvement. It also changed the exact quality tuples for
problems 245, 287, and 931 in the fixed ten-problem subset. The implementation
was removed; retain the sparse block-diagonal representation.

Persistent block-edge topology follow-up
----------------------------------------

Status: implemented and retained after a fixed ten-problem benchmark.

The scalar block-edge Schur operator retained in item 13 previously rebuilt,
sorted, and merged camera-landmark edges for every normal-equation evaluation.
The program now constructs the unique sorted topology and observation-to-edge
mapping once in ResetProgram. Every evaluation clears the persistent 9x3 edge
values and accumulates directly into the mapped edge.

All ten problems reproduced bestCost30, bestCost60, final cost, and best
iteration exactly. Relative to the fresh block-edge baseline, performance
improved by:

  geometric-mean overall:    11.88 percent
  aggregate overall:         19.53 percent
  geometric-mean solve-only: 13.12 percent
  aggregate solve-only:      21.54 percent

Keep this optimization.

The fixed benchmark subset is problems 52, 142, 245, 287, 394, 646, 744, 931,
1064, and 1266, each run for 90 iterations with 30 clusters. The reusable
runner is run_optimization_subset.sh.

17. Reduce protobuf copies and allocations
------------------------------------------

Use const references for request submessages while request_p remains alive:

  const auto& update = request_p.update();
  const auto& pro = request_p.program();

All data required by detached workers is already copied into CeresProgram
before request_p leaves scope; worker lambdas receive only IDs.

In FillReturnProto, reserve repeated-field capacity before appending cameras,
landmarks, and full_stepSize. Use range insertion for cameras and full_stepSize
where supported. full_stepSize contains 81*numCameras doubles on every return,
so avoiding repeated protobuf growth may be measurable.

18. Replace detached request threads with a fixed worker pool
-------------------------------------------------------------

The 30-cluster, 90-iteration configuration creates thousands of detached OS
threads. A fixed pool would remove thread creation/destruction overhead, make
the concurrency limit explicit, and provide safer shutdown and object
ownership. This is expected to be secondary to Jacobian and Schur work but may
reduce timing variance.

19. Remove inactive custom-path Ceres setup
-------------------------------------------

In the active custom solver path, function_residual_blocks is captured before
ProxStepPrior residual blocks are added. GetJacobianAndResidual and GetCost
evaluate only function_residual_blocks, so the ProxStepPrior blocks and their
81-value stepSize parameter blocks are setup and memory overhead but do not
participate in these evaluations.

Condition their construction on the Ceres solver path, or remove them from the
custom path after confirming that no request mode depends on them. Expected
runtime benefit is small because this primarily affects program setup.

20. Benchmark native CPU and link-time optimization
---------------------------------------------------

The current server uses -O3 -DNDEBUG and targets generic x86-64. On a fixed
deployment machine, benchmark:

  -march=native
  -flto

These flags may improve fixed-size Eigen and autodiff code. Keep this as a
separate benchmark because the resulting binary may not be portable to older
CPUs.

21. Batch weighted cost evaluation
----------------------------------

Status: implemented and retained after ten-problem and full-suite validation.

GetCost previously dispatched every observation through Ceres even though it
requested only the scalar cost. The weighted path now transforms each camera
and landmark once, evaluates all observations directly, and accumulates the
same half squared residual cost expected from Ceres.

On the fixed ten-problem subset, bestCost30, bestCost60, final cost, and best
iteration matched exactly. Relative to the retained workspace-reuse baseline,
performance improved by:

  geometric-mean overall:     8.60 percent
  aggregate overall:         10.68 percent
  geometric-mean solve-only:  9.35 percent
  aggregate solve-only:      11.81 percent

22. Batch weighted normal-equation evaluation
---------------------------------------------

Status: implemented and retained after ten-problem and full-suite validation.

The active weighted normal-equation path no longer dispatches residual blocks
through ceres::Problem::Evaluate or constructs a CRS Jacobian. It transforms
each camera and landmark once, evaluates observations in a direct loop, and
accumulates U, V, W, bp, and bl into the existing persistent buffers.

The implementation still uses ceres::Jet<double, 12> for the nonlinear BAL
projection derivatives. The weighted camera and landmark chain-rule seeds are
inserted directly, preserving Ceres derivative behavior while removing the
general residual graph and CRS machinery.

On the fixed ten-problem subset, all four quality fields matched exactly.
Relative to the retained batched-cost implementation, performance improved by:

  geometric-mean overall:    15.76 percent
  aggregate overall:         19.10 percent
  geometric-mean solve-only: 17.56 percent
  aggregate solve-only:      21.36 percent

The combined batched evaluators were then run on the canonical 29-problem
suite at 90 iterations and 30 clusters. Every problem matched its latest
pre-experiment bestCost30, bestCost60, final cost, and best iteration exactly.
Relative to those pre-experiment records, performance improved by:

  geometric-mean overall:    44.14 percent
  aggregate overall:         62.65 percent
  geometric-mean solve-only: 50.40 percent
  aggregate solve-only:      76.45 percent

The full-suite runner is run_optimization_full.sh. Keep both optimizations.

23. Preserve the generic evaluator and test batched-loop cleanup
---------------------------------------------------------------

Status: generic fallback retained; three performance experiments rejected.

The specialized weighted L2 evaluator remains the default, but setting:

  BUNDLE_PALM_BATCHED_EVALUATION=0

routes both cost and normal-equation evaluation through the existing generic
Ceres residual-block path. A 30-iteration problem 52 check reproduced the
established best cost 485348 at iteration 29. This keeps the implementation
open to other residual models and loss functions without requiring the
specialized evaluator to support them first.

Three independent batched-loop optimizations were tested on the fixed
ten-problem subset. Every experiment reproduced bestCost30, bestCost60, final
cost, and best iteration exactly, but none passed the timing gate:

  cached camera derivative seeds: 0.9875x geometric-mean solve-only
  triangular Hessian accumulation: 0.9885x geometric-mean solve-only
  scalar residual norm only:       0.9860x geometric-mean solve-only

All three performance changes were removed. Their extra passes, storage, or
bookkeeping cost more than the arithmetic they eliminated on this workload.
Retain only the runtime evaluator selector.

24. Index scalable-partitioner evacuation backfill candidates
--------------------------------------------------------------

Status: implemented and retained after exact partition and end-to-end checks.

The scalable landmark partitioner's evacuation phase searched for balancing
backfill by scanning the global landmark order and discarding landmarks not in
the target cluster. On large balanced problems this inspected roughly thirty
times more order entries than candidate landmarks. The scan is repeated for
many camera-cluster pairs and dominated partition time for problems 961 and
3068.

State now maintains one dynamic landmark-rank bitset per cluster. ApplyMove
updates two bits in constant time, and evacuation enumerates set ranks in the
same global order. Candidate scoring, the 4096-candidate limit, move ordering,
and all partition objectives remain unchanged.

A std::set prototype preserved assignments but was 3.4 percent slower on
problem 961 and was removed. The bitset implementation produced byte-identical
landmark assignments and identical partition metrics:

  problem 961 native partition:  55.18 s -> 45.61 s (1.210x)
  problem 3068 native partition: 101.86 s -> 79.83 s (1.276x)

End-to-end 90-iteration, 30-cluster validation reproduced bestCost30,
bestCost60, final cost, and best iteration exactly:

  problem 961 partition: 54.38 s -> 45.43 s; overall 131.42 s -> 122.66 s
  problem 3068 partition: 101.88 s -> 79.23 s; overall 204.64 s -> 183.63 s

Keep this optimization.

25. Compile the local clustering library for the host CPU
-----------------------------------------------------------

Status: implemented and retained after exact partition checks.

The standalone clustering library built by build_local.sh now uses
-march=native. This enables the host instruction set for the evacuation and
scoring loops. It makes the generated shared library specific to CPUs
compatible with the build host; rebuilding on the deployment host remains
required.

Against the retained dynamic-bitset implementation, complete landmark
assignment hashes remained identical:

  problem 961 partition:  45.05 s -> 36.78 s (1.225x)
  problem 3068 partition: 79.56 s -> 62.72 s (1.268x)

The established ten-problem subset also reproduced every complete assignment
array. Its aggregate partition time improved from 39.85 s to 38.34 s (1.039x),
with all ten individual timings improving in the measured run.

An independent attempt to replace the backfill camera-membership std::find
with a dense landmark stamp was rejected. It preserved assignments but changed
961 by 0.982x and 3068 by only 1.012x, so it was not a consistent improvement.

Adding -flto on top of -march=native was also rejected. Reversed-order tests
were mixed: it slightly helped 961 but slightly slowed 3068, so there was no
reliable incremental benefit.

Keep the native build flag for local builds. Do not add the membership stamp.
